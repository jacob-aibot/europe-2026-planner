2What is already built▾
  • The trip engine — days, stops, legs, cost roll-up, map clustering, conflict detection, validation, import/export, and provenance tracking (who a piece of data belongs to). No external dependencies, fully deterministic.
  • The save/persistence layer — decides when an edit is safe to write, refuses to overwrite a concurrent edit, never silently drops something you typed. This is the part that took 7 adversarial rounds to get right (see §6).
  • The web app — opens in a browser, loads your real trip, supports multiple trips, day editing, a day map, a conflicts panel, and copying one stop from another trip with credit attached.
  • A command-line tool for inspecting a trip, its conflicts and costs with no browser at all — what QA uses to check the engine directly.
  • 387 automated tests, all passing (up from 333 as of the latest builder pass), plus a separate stack of adversarial probe scripts built specifically to try to break named claims.

6Recent progress (R2–R7)▾

Short version: seven rounds of one QA tester repeatedly trying to break the save/persistence layer — and finding a real way to lose data almost every round, until round 6.

  • R2 — closed a lost-edit race, a stop that could vanish, and a leaked credential in a copied note.
  • R3 — found the "is this still safe to save" check could be spoofed by delete-then-recreate.
  • R4 — found the R3 fix had the same bug one layer upstream (undo + a new edit could skip a write while showing "Saved").
  • R5 — found an edit made mid-check could be silently discarded, and a blank "who did this" field slipping past a check.
  • R6 — verified R5's fixes by deliberately breaking them again and watching tests fail correctly; found a silent give-up-after-retrying path.
  • R7 — verified everything again, closed the last serious save-path bug, found three narrow issues not reachable by a user yet.
  • Gate review — looked at the actual screens for the first time in five rounds and sent Phase 1 back for 3 disclosed-but-unfixed gaps.
  • SEND-BACK pass — the builder just fixed all 3 gaps plus 4 smaller items in one pass, 387 tests passing. Independent verification of this pass hasn't happened yet.

Why so much verification before Phase 1 counted as close to ready: each of these was a way an edit could be silently lost or corrupted — the worst thing a trip planner can do. Each fix was immediately attacked rather than trusted, which is why several "closed" bugs reopened one layer up. That's expensive, and it's the only way to actually trust the result.

10Definition of "done"▾

Code existing is not the same as a phase being shipped. There's a four-stage pipeline — architect → builder → breaker → manager — precisely because "the builder says it works" was never enough on its own.

A phase is complete only when:

  • its acceptance criteria are met, written so they can't pass by accident;
  • an adversarial tester tried specifically to break it, and it's written down, not assumed;
  • the manager reviewed the actual product — not just the test count — and recorded a verdict of SHIP.

Phase 1's engine and save logic are built and verified, genuinely, by that standard. The three screen gaps the manager sent back are now built — that's not the same claim as verified (needs an independent breaker round) or shippable (needs a manager verdict of SHIP). All three are real, different claims, and this page tries to always say which one it means.
